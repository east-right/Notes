## 언어모델
언어모델 = 어떤 단어가 등장 해야 자연스러운지를 판단할 수 있는 모델, 이를 LM(Language Model)이라고 하며 초기에는 확률에 기반한 모델이 주를 이루었고 RNN + Seq2Seq를 거쳐 Transformer 기반인 지금 까지 왔다.
Transformer은 Encoder와 Decoder를 기반으로 이루어진 모델이며 현 LLM시대에는 트렌스포머 형태를 유지하지 않고 Encoder와 Decoder를 분리하여 각각의 강점이 최대한 살리는 방향으로 사용 중이다.
트렌스포머의 대표적인 모델은 BERT와 GPT가 존재한다.
- BERT
	- 구글이 제안한 방식으로 Encoder model의 대표격
	- 인코딩 모델들은 주로 임베딩 모델에 많이 사용된다.
	- 장점
		- 이해에 강하다.
		- 분류, 추출, 임베딩 모델에 상대적으로 뛰어난 성능을 가짐
	- 단점
		- 생성에 적합하지 않음, 즉 글쓰기와 같은 답변을 생성하는 기능을 매우 제한적임
		- 그로 인해 RAG시대인 지금은 임베딩 모델로 많이 사용됨
- GPT
	- 디코더 모델의 대표격이자 LLM 시대를 연 장본인
	- 우리가 아는 LLM 들은 전부 디코더 모델이며 그중 대표가 GPT
	- 장점
		- 문장을 생성하는 능력에 특화
		- 이 문장을 생성하는 능력이 고도화 되고 학습량이 많아지지만 인코더 모델 못지 않은 자연어 이해 능력을 보여준다.
	- 단점
		- 문장을 이해하는 능력을 부여하기 위해선 많은 비용과 리소스가 소모
		- 그래서 임베딩 모델에도 사용이 가능하지만 임베딩 모델에는 주로 사용하지 않음(논문은 있다고 함)
- t5 혹은 BART
	-  인코더 디코더 두 개다 사용하는 모델
	- 전반적으로 LLM 시대에 생성은 GPT에게 이해는 BERT에게 밀린다.
	- 하지만 **충분히 사용 가능한 모델이다. 문제 주제에 따라 LM 모다 합리적인 선택이 될 수 있다.**
>질문: 왜 디코더만 거대화 시켜서 LLM을 만드냐? 어차피 리소스를 고려하지 않는다면 인코더 디코더 구조를 사용한 t5를 거대화 시키는 게 더 옳은 거 아니냐?
>
>답변: *작성바람 이거 찾아보면 있음*

> openai의 창업자들이 자기들이 구글에 있을 때 모델을 만들때 모델이름을 gpt로 명명을 먼저함이걸 구글 퇴사하면서 창업할 때 gpt라는 걸 자기들 브랜딩으로 밀고 싶어 했는데 법정소송에서 졌음 ㅋㅋ

## 토크나이저와 임베딩
컴퓨터에게 글자를 알게 할려면 기본적으로 문자를 숫자로 변환해야하는데 이 때 문장을 통으로 넣는게 아니라 특정한 규칙에 따라 나누고 그걸 숫자로 변환하는데 이걸 토크나이저라고함
![](assets/Pasted%20image%2020250106210446.png)
이 토크나이저는 LLM의 성능에 매우 지대한 영향을 미친다. 옜날에는 각 언어의 특성을 이용하여 잘랐는데 이걸 형태소 분석이라고 한다.
하지만 형태소 분석이 LLM 시대에선 주류로 사용되진 않는다. 현재 토크나이저에 가장 기본이 되는 개념은 Byte-pair Encoder로 음절로 쪼개어 자주 등장하는 쌍은 합치는 방식을 사용한다.
이제 이렇게 쪼갠 단어를 컴퓨터가 알아 들을 수 있는 벡터(숫자)로 변환시키는 과정을 임베딩이라고 한다. 
임베딩은 직접 공개된 모델을 다운하여 사용하거나, API로 제공받는것 총 두 가지 이다.
각 모델과 회사마다 사용하는 임베딩 모델이 다르고 결과도 다르기에 파인튜닝시에는 동일 임베딩 모델을 사용해야한다. sk 에선 임베딩 모델을 학습시키면서 BPE + 형태소 분석 기법을 두 개 혼합하여 사용한다는 걸로 안다.
대기업에서 개발한 한국어 임베딩 모델은 토큰화를 BPE와 같은 SubwordTokeniner 모델을 사용을 하되 최대한 형태소 분석 느낌이 나게 구성한다. 그렇게 해야 토큰 수를 최대한 줄일 수 있다. 
> 임베딩 모델과 LLM 모두 벤치마킹은 너무 맹싱하지 말것 그냥 유명한 모델을 탐색하는 용도로 사용하는게 적당하다.

## RAG
임베딩된 단어는 벡터 형태로 바뀌며 **컴퓨터가 알아들을 수 있고 계산를 구할 수 있게 된다.**
RAG라는 기술의 등장으로 인해 VecDB에 대해서도 조금 알아야 한다. RAG(Retrieval-Augmented Generation)느 RAG에서는 사용자가 질문을 던지면 질문과 연관되어져 있는 문서들을 찾아낸다 (검색기가 존재.) 검색 결과를 바탕으로 LLM에게 질문에 대한 답변을 요구한다.
RAG의 장점으로는 아래와 같다.
	• 검색된 내용을 바탕으로 ‘답변’하므로 내 데이터만을 이용하여 답변하는 챗봇을 구현 가능.
	• 챗봇이 거짓말하는 현상인 ‘할루시네이션’을 급감시킬 수 있는 효과.
RAG의 성능은 문장/문서 간의 유사도를 얼마나 잘 판단하나이다. 그래서 hdye와 reranking와 하이브리드 서치, 임베딩 모델 파인튜닝도 매우 자주 시도한다.
한국어가 잘되는 임베딩모델의 대표는 아래와 같다.
- BGE-M3
	- 한국어가 잘 되는 임베딩 모델 중에선 제일 유명하고 많이 사용
- e5
	- 이 모델 또한 위의 모델에 버금가는 정도로 모델 임베딩이 잘된다.
	- 하지만 max_token 길이가 짧다.
만약 키워드 기반으로 유사도를 찾을 땐 bm-25알고리즘이 최고다.
### 토큰 임베딩과 문서 임베딩
강의 PPT에서 RAG를 할 때 기본적으로 임베딩 방식은 문장/문서 임베딩을 전제로 설명을 했다. 하지만 임베딩은 그 목적에 맞게 단어/문장/문서 임베딩으로 나뉜다.
이 임베딩은 자주 헷갈릴 위험이 매우 높은데 각각의 임베딩은 아래와 같이 정의되고 나뉘어진다.
- 단어/토큰 임베딩
	- 모델의 입력으로 주로 사용
- 문장/문서 임베딩
	- 모델 출력의 결과
	- RAG를 사용할 때 주로 사용

## 모델링
오픈 소스 모델 기준으로 주로 사용하는 모델이 qwen, llama, gemma가 있다. **개중 qwen과 llama 한국어에 강하다.**
허깅페이스에서 모델을 load했을 때 가장 중요하게 확인해야하는 부분은 max_position_embeding과 같은 max_token의 길이와 학습 때 사용된 prompt_template의 형태이다.
아래는 llama의 prompt의 예시이다.
```
messages = [
    {"role": "system", "content": "당신은 인공지능 어시스턴트입니다. 묻는 말에 친절하고 정확하게 답변하세요."},
    {"role": "user", "content": "은행의 기준 금리에 대해서 설명해줘"}
    {"role":`"assistant", "content": "금리란 금리다." `}
]
```
llama는 학습 데이터를 구상할 때 위와 같은 형식으로 넣는 것이 권장된다. 여기서 제일 중요한건 **질문을 하는 role: User를 적고 뒤에 role: assistent, 'content': 를 명시하는게 성능적으로 매우 좋다는 점이다. 학습 데이터에 assistent가 명시된 모델은 assistant에 답변을 적게 학습이 되어있어 assistant가 명시되어 있지 않으면 아직 질문이 끝나지 않은 것 혹은 질문 뒤에 문장을 생성해야하는 문제로 인식할 수 있다.**
**assistant를 사용하는 모델은 assistent가 있지 않을 시 학습이 매우 불안정하다. 만약 내용이 없으면 해당 내용없음 과 같이 내용을 넣어주는 게 좋다.**
모든 모델의 템플릿은 각 모델의 공식 document 사이트에 공유가 되어 있다. 물론 langchain으로 모델을 불러와서 넣으면 입력 input이 자동으로 해당 모델에 맞게 템플릿이 작성이 된다.

Q: 데이터의 크기가 크지 않을 때 풀 파인튜닝이 좋냐, 아니면 LoRA 어뎁터 기반 부분 파인튜닝이 좋냐?
A: 파인튜닝은 풀 파인튜닝과 컨티뉴얼 파인튜닝(이거 논문이 있어서 학습 리뷰 예정)이 존재하는데 instruction 질답 형식으로 데이터를 학습할 땐 기본적으로 LoRA가 월등하다. 풀 파인튜닝은 **자연어 데이터가 서적 혹은 논문과 같이 안의 내용과 맞춤법과 줄바꿈이 꼼꼼히 지켜진 질 높은 데이터에 적합하다.** KMLU는 한국어에 대한 성능 평가가 존재하는 이거를 해보니 데이터를 거르고 거르고 넣었을 때 풀파인튜닝이 그나마 올라감
그리고 데이터가 2~3만 이면 몰라도 2~3천이면 풀 파인튜닝하기에는 부족하다.

Q: Faiss의 유사성 검색 알고리즘들인 HNSW 혹은 LSH+PQ와 같은 ANN 기반 알고리즘 들도  RAG시에 주로 활용하나?
A: 이건 RAG로 탐색해야하는 데이터의 양에 따라 판단해야한다. ANN 기반은 모든 데이터를 탐색하는게 아니라 근사값을 기준으로 하기에 속도가 높을 순 있지만 기본적으로 쿼리 결과 성능은 조금 떨어지고 GPU 자원을 잡아먹는다. RAG 문서 양이 크지 않으면 그냥 COS유사도로 하는게 좋다.
