## Langchain
사실 RAG 할 때 Langchain이 필수인가? 라고 항다면 그 답은 결코 아니다. 코드를 매우 간소화 시켜준다는 장점이 존재하지만, llama index를 사용하거나 큰 프로젝트와 같은 경우 앞으로의 유지보수가 매우 중요하므로 배제하는 경우도 다분하다.(허깅페이스는 필수필수)
**RAG 공부의 시작은 Langchain이 적합하지만 RAG 프로젝트를 수행하고자 하는 사람들은 LLM과 RAG 그 자체의 본질에 대해서 공부가 필요**
Langchain의 아쉬운점
- 테이블과 표가 가득한 헬 난이도의 PDF 문서의 전처리
- 보안 상의 이유로 GPT4가 아니라 LLamA와 같은 오픈소스 모델을 사용할 때
	- 파인 튜닝을 하면 RAG 성능의 상당 부분 UP이 가능 하지만 Langchain은 prompt 입력시 role을 기입을 잘안해서 prompt에 가장 중요한 role에 대한 튜닝이 어려움
- Agent RAG 활용시
	- Langchain에서 기본 세팅된 prompt 들은 정말 성의가 없다. 그래서 직접 작성하는 경우가 많음, 도큐먼트 페이지도 정보가 부족함
	- 따라서 에이전트 자체에 대한 이해도가 요구되고, 재시도, 도구 성택 등 각종 Agent RAG에는 다양한 다수의 모델을 상황에 맞게 파인 튜닝 해야함
	- Agent 엔진 커스텀 영역으로 들어가게 되면 이때부터는 에이전트 지식이 있는 백엔드 엔지니어 채용 필요
![](assets/Pasted%20image%2020250108125227.png)
> 기본 GPT Prompt 형식과 Langchain 형식

- System: LLM에게 시지고자 하는 역할을 명확히 지시하는 구간
- User: 유저의 질문
- Assistent: 챗봇의 답변
## 청크(chunk)
하나의 긴 문서가 있을 때 이를 RAG로 구현하기 위해서는 긴 문서를 작은 문서들로 분할하는 작업을 청킹 (Chunking)이라고 한다. 청킹 후에 이 분할 된 각각의 문서들이 임베딩이 되어 벡터 DB에 적재된다.
Langchain에서 제공하는 대표적인 청크
- RecursiveCharacterTextSplitter 
	- 길이 단위로 자른다. 따라서 문맥이 중간에 잘리는 구간이 발생할 수 있다.
	- 이에 따라서 자를 때 내용이 겹치도록 하는 chunk_overlap을 지원하나 임시 방편 수준. 
- SemanticChunker
	- OpenAI의 임베딩 API 등… 임베딩 모델을 이용하여 모델을 문맥 별로 자른다.
	- 문맥 별로 자르면 이상적으로는 좋은 성능을 얻을 수 있지만, SemanticChunker 성능 자체는 애매함
보통 문맥을 고려하여 청크를 나줘 주는 모델을 큰 회사에서는 따로 청킹 전략 모델을 1개씩 구현을 하고 가지고 있는 경우가 대부분임
청킹 전략
1. LLM Base Chunker
	-  Prompt 엔지니어링이 동반되어야함
	- 사람이 자르는 것과 비슷한 효과를 내기 위해서 LLM 자체를 Chunking에 사용하는 전략
	- 좋은 성능의 LLM을 활용하여 Prompt Eng를 통해 작업
2. PLM Base Chunker(Fine-tuning)
	- NLP 엔지니어라면 T5와 같은 모델로부터 이어지는 두 개의 문장 내지는 문단을 주고 판단하도록 학습한 후, 일종의 임계값으로 조절하면서 꽤 뛰어난 Chunker를 구현하는 능력을 기를 필요가 있음
	- Langchain의 기본 SemanticChunker의 정교한 커스텀 버전
3. 합성 데이터 방식
	- 주어진 문서로부터 새로운 문서를 만들어서 이 데이터를 벡터 데이터베이스에 적재하는 전략
	- QA방식, 앤트로피의 Context Retreival 방식, RAPTOR논문 방식 등등
	- 잘 사용하면 굉장히 강력함, 몇가지 테크닉을 이용하면 장기 의존성 문제를 해결가능
	- GraphRAG 이상의 성능도 나올 가능성이 있음
>합성 데이터 방식(RAG에 사용될 도큐먼트가 PDF 가정)
>1. 50페이지의 PDF가 존재한다 가정
>2. 그럼 PDF의 두 페이지씩 묶음 ex [1,2], [2,3], [3,4] .... [n, n+1]
>3. 그런후 LLM에게 한 묶음식 Prompt를 제시하면서 사용
```
이어지는 2개의 페이지로 부터 FAQ를 5개 만드시오
단, 아래의 FAQ 5개는 이전에 만들어진 내용이므로 아래 내용과 겹치는 내용은 빼세요
FAQ에는 몇 페이지에서 만들었는지 출처를 명시하시오
이어지는 페이지는 연결된 내용일 수 있으므로 두 개의 페이지를 모두 사용하여 하나의 FAQ를 만들 수도 있다.
질문: ~~~
답변: ~~~
```

## 리트리버(Retiever)
랭체인의 가장 큰 장점은 서로 다른 패키지의 벡터db를 들고와도 Langchain에서 제공하는 패키지로 인해 동일한 코드로 작성이 가능하다는 점임
키워드 기반 검색
- 임베딩(문서/문장) 기반의 검색에만 의존할 필요는 없다.
- 기존의 검색엔진에서 사용하고 있는 키워드 기반의 검색을 함께 사용하는거도 좋은 전략이다.(하이브리드 서치)
- 키워드 기반 검색이 BM25 알고리즘을 많이 사용한다.
Reranking
- 검색을 두 번 수행하여 검색 성능을 높이는 방법
- 두 번째 모델은 '크로스 인코더'를 사용
- 두 개의 임베딩 모델을 파인튜닝하면 해당 도메인에선 최고의 검색 성능을 보여준다.
기회 될 때 [A Closer Look at Rehearsal-Free Continual Learning](https://velog.io/@anandh/A-Closer-Look-at-Rehearsal-Free-Continual-Learning)(컨티뉴얼 튜닝)을 공부해라
> 질문 타임
> Q. 풀 파인튜닝을 하고 kmlu로 벤치마킹 성능을 체크하니 성능이 떨어지더라 ?
> A. 글로벌 언어를 학습한 모델은 풀 파인튜닝을 하면 기존 보다 한국어 성능이 떨어지는 경우가 있는데 이 문제는 학습 데이터의 퀄리티 문제이다. 전공 서적 혹은 교과서 같은 정제된 문장들을 학습데이터로 넣으면 성능이 올라감
> 그리고 학습을 할 때는 Instruction Tuning을 해라
> Q. Langchain으론 이전 대화 로그를 못 집어 넣냐?
> A. 보통 사람은 최근 대화에서 이루어진 주제를 가지고 다음 대화도 이어간다. 그래서 보통 코드를 짤 때 이전 대회 기록 모두가 아닌 일부만 답변을 생성할 때 참조하는데 ChatGPT는 Assistant로 가능하지만 Langchain에선 그러한 기능이 없다. 그래서 보통 강사님 본인은 직접 코드를 짜신다.
> Q. 청킹 전략을 보통 뭘 사용하시냐
> A. Langchain Text 분할기는 본인은 추천하지 않지만 많이 사용하고 빠르게 프로토타입을 만들거나 할 땐 사용한다. 데이터를 임베딩 할 때 혹은 청크해서 넣을 때 최대한 LLM으로 정제하는 것이 좋다. Lanhchain을 사용할 때 promptTamplate를 지정하지 않고 직접 role을 주는 디폴트 Tamplate를 사용하는걸 권장한다.

## Rerank
첫 번째 검색이 끝나고 나서 두 번째 검색을 한번 더 해서 순위를 조정하는 방식
보통 임베딩 모델을 두 개를 사용한다.  보통 첫 번째 검색 때는 가벼운 임베딩 모델 두 번째 검색 때는 성능이 좋고 무거운 임베딩 모델을 사용한다.
리랭킹의 두 번째 모델은 보통 첫 번째 모델을 통해 걸러진 결과를 바탕으로 다시 유사도 랭킹을 매길 때 사용된다.
보통 임베딩 모델은 **Bert 기반의 모델이 사용되는 데  BGE-M3도 Bert 기반 모델이다.**
![](assets/Pasted%20image%2020250108144846.png)
Bert 기반 임베딩 모델은 두 가지 유형이 존재한다. 하나는 문장이 들어오면 그걸 개별로 모델에 넣어 임베딩 벡터를 받는 모델 Crosse는 두 문장이 들어오면 두 개 다 하나의 모델에 넣어 Bert의 능력중 하나인 분류 문제를 풀게 지정한다.
보통 Cross 기반 인코더가 유사도 기반 문제에선 더욱 좋은 성능을 보인다. 하지만 Cross 기반 인코더는 문장 임베딩 벡터를 제공하지 않기에 무조건 두 문장이 쌍으로 들어가야 한다.
이로인해 Cross 기반 인코더 임베딩 모델은 Rerank 시에 첫 번째 모델로 사용될 수 없다. 문장 임베딩 결과를 제공하지 않기 때문이다.
그래서 Rerank를 사용할 땐 첫 번째 문장으로 bi 모델을 사용하고 나온 결과를 Cross 임베딩 모델에 넣어 최종 RAG 결과를 받아 본다.
**BGE-M3 모델은 논문을 읽어 보면 알겠지만 bi 기반 모델이다. 하지만 Cross 기반 모델로 파인튜닝 되서 나온 모델이 존재하는데 이 모델은 뒤에 Reranker라는 수식어가 붙어 있다.**

## 질의 변형(Hyde)
기본적으로 사용자의 질문인 쿼리의 길이는 짧고, 우리가 찾아야 할 검색 문서의 길이는 길다. 질의 변형은 hyde라는 논문에서 최초로 제안한 방식이며 **LLM이 사용자의 질문에 대해 임의로 '답변하고 그 '답변'으로 검색을 하도록 하는 방법이다.**
즉 질문:답변 의 유사성을 검색하는 것이 아니라, 답변:답변으로 RAG 문서를 검색하는 방법이다.
이 방식의 가장 큰 장점은 LLM이 준 내용과 검색문서의 내용이 길이 혹은 핵심 키워드들이 비슷하게 나오기에 검색 성능이 높아진다.

## 멀티턴과 멀티 쿼리
**멀티턴**이란 이어지는 대화에서 이전 대화를 반영하여 검색을 수행하도록 하는것을 의미한다.
종종 우리는 LLM 서비스를 할 때 부족한 정보가 있으면 웹 검색을 통하여 추가적인 정보를 얻고 답변에 활용한다. 
이때 사용자가 원하는 내용을 담고 있는 검색어 선정이 중요한데 아래의 사진과 과 같이 이전 대화를 반영하지 않고 웹 검색을 실시하면 엉뚱한 정보를 검색할 위험이 높다.
![](assets/Pasted%20image%2020250108135928.png)
그래서 이러한 상황을 해결하기 위해 이전 대화 기록을 입력에 반영하는걸 멀티턴이라고 한다.
**멀티턴 RAG를 구현하는 방법은 여러가지 방법이 존재한다.** 대표적으로 ReACT Agent, 별도의 이전 대화 반영 모델 등...
기본적으로 이전 대화를 누적 입력으로 사용하여 검색어를 정제하도록 하는 것을 동일한 원리이다.
![](assets/Pasted%20image%2020250108140107.png)
**멀티 쿼리**의 경우 'A와 V와 C를 알려줘'와 같이 동시에 알려달라고 하였을 때 이를 적절하게 쿼리를 분리하여 수행하는 능력을 의미한다.
멀티 쿼리 또한 멀티턴과 마찬가지로 별도의 모델을 두는 것이 가능하다. 이 내용은 이 때 설명하지 않고 나중에 Agent에서 설명한다.
