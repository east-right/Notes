## RAFT
저번 자연어처리 기본 시간에도 강조하고 이번 LLM RAG에서도 강조하는 RAG 파인튜닝의 RAFT이다. 기본적으로 RAFT는 RAG 상황을 고려한 **LLM model Fintuning**방식이다. 한창 잘 모를 때는 Rag에 Negative, Positive 나와서 임베딩 모델 파인튜닝 이야기 하는 줄 알았다.
RAG시 쿼리가 들어왔을 때 유사도가 높은 값을 기반으로 document를 정렬한다. 더욱 좋은 Rag 결과를 위해 Rag에 특화된 임베딩 모델을 사용하기도 파인튜닝까지 한다. 하지만 쿼리와 document의 유사도가 항상 사용자가 원하는 결과로 나오지는 않는다. 
이러한 상황을 가정하여 LLM 모델을 파인튜닝 할 때 Prompt에 Rag 탐색의 안좋은 결과까지 고려하여 Negative documnet까지 함께 넣어서 학습을 시키는 방법을 말한다.
**RAFT는 기본적으로 연관된 문서(Positive) + 연관되지 않은 문서(negative) 문서를 들고와 CoT prompt를 구성하여 답변을 제시하여 파인튜닝을 한다.**
![](assets/Pasted%20image%2020250115205307.png)
이러한 방식은 모델에게 Prompt에 답변과 관련이 없는 정보가 있음을 인식시키고 결과적으로 올바른 답변 생성 능력을 향상 시킨다. 이 때 Negative 문서와 Positive 문서는 CoT 형식으로 각 문서를 분류한다. 
![](assets/Pasted%20image%2020250115210107.png)
위 사진과 같이 RAFT는 CoT에 원문 인용을 시킨다. Rag로 탐색한 문서를 들고와서 Prompt에 넣고 CoT 형식으로 지시사항에 따라 추론을 하고 최종 답변까지 제시하는 것을 데이터로 구성하고 학습시킨다. 여기서 위 사진과 다르게 Negative documnet도 입력 데이터 Prompt에 넣어 CoT에 해당 내용이 없다는 추론 내용을 작성하여 집어 넣는다.

### RAG 특화 모델
#### Cohere
이미 Rag에 대해서 학습된 오픈소스 RAG 특화 모델들이 존재하는 데 이러한 모델들을 확인하면 RAG 특화 Fintuning할 때 Prompt를 어떻게 구성해야 할지 힌트를 얻을 수 있다. 예를 들어 Cohere라는 회사에서 만든 Command R, Command R,+가 이에 해당한다. 
![](assets/Pasted%20image%2020250115211136.png)
![](assets/Pasted%20image%2020250115211259.png)
Prompt를 살펴보면 RAFT와 매우 비슷하단걸 알 수 있다. 위 사진으로 보아 cohere에서 제공하는 모델의 RAG Prompt에는 아래와 같은 특징이 있다.
- 답변시에 쿼리와 관련된 문서를 답변에 기록하게 지시
- 답변에 문서의 인용을 강제하고 인용한 문서의 번호를 표시
- 답변 생성을 총 2회 시키며 처음에는 일반적으로 답변을 생성 시키고 두 번째로는 답변의 내용이 어느 문서에서 인용하였는지 기록한다.
이러한 cohere의 강제적인 인용 Prompt는 모델의 할루시네이션을 감소시키는 효과가 있다.
또한 RAFT와 다르게 스페셜 토큰을 적극적으로 사용하여 어느 문서에서 인용했는지 기록하게 시켜서 인용을 강제를 더욱 강제시킨다.
#### orion
orion은 기본적으로 다양한 Task에 맞춰서 파인튜닝된 모델을 공개해 주고 이중 cohere와 같이 Rag 특화 모델이 존재한다. 
![](assets/Pasted%20image%2020250116101520.png)
orion에서 제공해주는 prompt를 보면 RAFT 방식과 같이 최종 답변 마지막에 답변에 대한 내용이 어느 문서에서 인용했는지 기록을 한다. 본 방법은 위 두 방식보다 강제성이 조금 떨어져 성능이 조금 떨어지지만 사용하지 않았을 때 보다 Rag로 인한 답변 성능이 좀 더 올라간다. 

위와 같은 문서의 인용을 강제하는 Prompt 방식의 장점 중 하나는 평가 시 정량적 평가 기준을 추가해주는 것 이다. 평가셋이 존재할 때 실제 정답 문서를 인용했는지을 확인해서 Rag의 성능을 평가가 가능한다.

### Rag 고도화 파인튜닝 데이터셋 제작 방법
10B 이내의 모델은 기본적으로 데이터셋에 매우 민감하다. RAG 파인튜닝을 한다면 아래와 같은 사항들을 반드시 준수하여야 한다.
- GPT-4 API 와 같은 고수준의 모델로 RAFT 방식을 사용하여 답변을 작성하도록 하고 small 모델에 레이블로 사용
- 질문과 상관업는 문서가 검색되었을 때를 가정하여 Negatice Sample을 반드시 잘 구축할 것
- 아래의 모든 유형의 데이터가 반드시 학습 데이터에 포함되어 있어야 한다.
	- 단답을 유도하는 구체적이고 지엽적인 질문
		- 11월 27일에 세미나가 열린 장소의 이름은 무엇입니까?
	- 단답이 아닐 수 있는 넓은 의미의 질문
		- 세미나의 주제는?
	- 명사구 형태로 끝나는 질문
		- 11월 27일에 세미나가 열린 장소
	- 영어에 대한 답변도 좋은 퀄리티로 받고 싶으면 영어로도 학습을 시킨다.
	- 검색 결과가 1개일 때, 2개일 때
	- 검색 결과에 질문에 대한 답이 전혀 없을 때(할루시네이션 방지)
	- 답변 시 검색 결과 중 1개의 문서만 인용하는 경우
	- 답변 시 검색 졀과 중 다수의 문서를 인용하는 경우

## 파인튜닝 합성데이터 생성 코드(RAFT형식으로 파인튜닝 혹은 임베딩 모델 파인 튜닝 할 때 사용)
데이터는 기계독해 데이터를 기준으로 설명 기계독해 데이터는 웹에 많으니 찾아서 알아서 사용
### 네거티브 데이터 선정 코드
- RAG 고도화 LLM을 만들 때 가장 중요 한 건 데이터이다. 10B 이하의 모델들은 데이터의 퀄리티에 많은 영향을 받기 때문이다.
- 데이터의 퀄리티 중 가장 중요 한 건 네거티브 문서 퀄리티이다. 네거티브 문서는 **유사도 측정을 하여 포지티브 다음으로 가장 유사도가 높은 문서를 해당 질문에 대한 네거티브 문서로 매핑한다.**
### 기계독해 질문을 그대로 사용하는 데이터
- 해당 코드는 위 `네커티브 데이터 선정 코드`를 타고 나온 데이터를 이제 파인튜닝 시킬 Prompt의 예시로 만들기 위해서 GPT-4 API를 통해 질문과 문서를 주고 답변과 답변에 인용한 문서 번호를 result로 받는다.
- 이 때 데이터를 구성 할 때 조심해야 하는 점이 두 가지가 있다.
	- 데이터를 구성 할 때 Positive 문서와 Negative 문서의 순서를 섞어야 한다. 항상 같은 순서로 Positive 문서와 Negative 문서를 넣으면 문서의 내용 보단 순서에 맞게 학습이 될 위험이 크다.
	- 검색된 문서의 수가 항상 동일한 개수일 수는 없다. 그래서 학습 데이터에 임의의 데이터들은 검색 문서를 4개 이하로 만든다.
-  이 소스 코드는 말 그대로 데이터 생성 코드이며 RAFT 형식을 염두해둬 질문/검색문서(포지티브, 네거티브 섞여있음, 순서도 섞임)/답변/답변 인용 문서 형식으로 만드는 코드이다.
### 넓은 질문 데이터
- 해당 코드는 넓은 질문을 만드는 코드이다. 여기서 말하는 넓은 질문이란 포괄적인 질문을 의미한다. 즉 하나의 질문에 답하기 위해 두 가지 이상의 문서를 참조해야하는 질문을 말한다.
- 이 코드는 데이터를 구성하기 위해 아래와 같은 가이드 라인을  따른다.
	-  다수의 문서를 제시(코드에선 5개 제시)
	- GPT에게 두 가지 이상의 문서를 참조해야만 답변 할 수 있는 질문을 생성해달라고 요구
	- 문서의 뭉치를 제공할 때 마다 5개의 질문을 생성 요구
	- 질문의 길이를 짧게 요구 -> 질문의 길이가 너무 길면 넓은 질문이 아니라 너무 많은 정보를 주어 오히려 질문이 문서에 너무나 종속됨
	- 모델의 성능을 높이기 위해 CoT 처럼 질문 생성시 근거를 작성 시킴
	- 그런 다음 결정 Actoin을 제시하는 데 이때 본인 스스로 검증을 시키기 위해 검증이 끝난 뒤 문단이 True or False를 기록하게 만듬
	- 이제 False가 나온 질문은 삭제 시킨 다음 위 `기계독해 질문을 그대로 사용하는 데이터`와 똑같이 GPT에 Prompt를 주어 답변을 생성한다.
	- **이 때 이 질문은 위 처럼 Positive 문서가 1개가 아닌 다수이기에 이점 유념하며 df를 구성해라(지금 생각해 보니 굳이 신경쓸 내용까지는 아닌거 같다.)**
- 이 코드의 핵심은 넓은 질문 생성 + 다수의 문서를 참조하는 데이터를 만드는 데 의의가 있다.
### 질문을 명사구로 패러프레이징한 데이터 
- 이 부분은 크게 어렵지 않다. 질문의 형태를 바꾸기 위한 코드이다.
- 예를들어 `일론머스크의 나이는 올해 어떻게 되나요?` => `일론 머스크 나이` 이런식으로 변환 하는 코드이다.
- 이거 또한 물론 GPT를 통해서 한다.
### 질문에 대한 답변이 없는 데이터
- 이 코드는 `넓은 질문 데이터`의 코드에서 Prompt의 목적이 답변할 수 없음으로 바뀐 버전이다.
- 답변할 수 없는 데이터도 무조건 만들어서 모델에 파인튜닝 시켜야한다.
- 그렇게 해야 할루시네이션을 예방 가능하다.

추가적 내용
- **만약 서비스가 영어에 대한 처리도 가능하게 하고 싶으면 영어로 된 데이터를 집어 넣어야 한다. 한국어로 파인튜닝을 하면 영어에 대한 처리 능력이 떨어지기에 영어를 처리하고 싶으면 영어로된 파인튜닝도 필수로 진행되어야 한다.**
- Negative는 최대한 질문과 유사도가 높은 문서를 선택하는 것 이 좋다. 이 유무가 성능에 꽤나 큰 영향을 미친다.
- 왜 가르쳐준 RAFT 형식으로 인용 강제를 안시킴? => GPT 생성 데이터로 RAFT 형식 데이터로 생성 유도하는 게 쉽지 않다.
### 임베딩 모델 파인 튜닝
- 임베딩 모델은 검색 성능을 높이기 위해서 파인튜닝을 한다
- nagative 문서는 연관은 있는데 내용이 포함되어 있지 않은 문서를 선정해야하한다.
- 여기서 llama_index를 사용한다. 물론 사용하지 않아도 된다.
- 여기서 핵심은 어떠한 데이터를 가지고 임베딩 모델 파인튜닝을 할 때 비슷한 도메인을 가진 데이터가 두 개 존재 할 때 한 개를 가지고 파인튜닝을 했을 때 나머지 다른 하나의 비슷한 도메인을 가진 데이터에 대해서도 결과가 향상이 되냐에 초점을 맞춘다.
- multypkeNegative를 쓰면 negative 문서를 만들지 않아도 된다.
- 또 다른 코드 파일에선 임베딩 유사도를 기준으로 네거티브 포지티브 문서를 지정해주는 코드가 있음
- 보통 임베딩 모델을 파인튜닝 할 때 먼저 rag를 구성하고 성능을 보고 파인튜닝을 하는데 이때 청킹이 잘 되어 있는 상황을 잘 가정해야한다
- 우리는 데이터를 잘안보고 하기에 네거티브이지만 그 내용이 포지티브일 확률이 존재한다. 이걸 예방하기 위해 LLM으로 한번 더 검증 방식을 거치는게 최고긴 한다.
