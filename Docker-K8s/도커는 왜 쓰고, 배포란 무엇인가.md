## 1. 먼저 "배포(deploy)"의 정의
- **실행(run)** = 그냥 프로그램을 돌리는 것 (내 노트북에서 uvicorn 띄우기).
- **배포(deploy)** = 그 서비스를 **실제 사용자가 24시간 접속 가능한 곳에 올려 운영**하는 것.

내 노트북은 운영처가 될 수 없다:
- 노트북 끄면 서비스 죽음 (항상 켜져 있어야 함)
- 공유기 뒤에 있어 외부 인터넷에서 접속 불가
- 다른 작업하면 자원을 뺏김

→ 그래서 배포는 보통 **항상 켜져 있고 인터넷에 열린 클라우드 서버**(AWS, Modal 등)에 올리는 것.
**배포의 본질 = 내 컴 → 클라우드 서버로 옮겨

## 2. 옮길 때 생기는 문제
클라우드 서버는 빈 리눅스 머신이다. 내 프로그램을 돌리려면 똑같이 다 깔아야 한다:
- 파이썬 버전 (서버엔 다른 버전이 깔려 있을 수 있음)
- torch, llama.cpp, fastapi… 버전 하나만 어긋나도 깨짐
- 시스템 라이브러리, 환경변수
- (이 프로젝트는) llama.cpp를 특정 CPU 명령셋(AVX2)으로 빌드까지 필요

손으로 서버마다 세팅 → **"내 컴에선 되는데 서버에선 안 돼요"** 지옥. 버전 미세 차이로 며칠 날림.
이것이 소프트웨어 배포의 고전적 악몽.

## 3. 도커가 하는 일 = 환경을 통째로 동결해서 옮기기
도커는 **앱 + 그게 돌아가는 데 필요한 전부(O 빌드된 llama.cpp, 코드)** 를
하나의 **이미지**로 봉인한다.

```
이미지 = [OS 베이스 + 파이썬 + torch + llama.cpp(AVX2 빌드) + 내 코드] 통째 동결
```

효과:
- 내 노트북에서 빌드·테스트한 **그 이미지 그대로** 클라우드 서버에서 `docker run` → **글자 그대로 똑같이** 돈다.
- 서버에 뭐가 깔려 있든 무관. 이미지 안에 다있으면 됨.
- "내 컴에선 되는데" 문제가 **원천 소멸** (된 그 환경 자체를 통째로 가져가니까).

## 4. 질문 정리
| 질문 | 답 |
|---|---|
| 도커 왜 씀? | 앱이 도는 **환경 전체를 동결**해 어디서든 똑같이 돌게. "내 컴에선 되는데" 박멸. |
| 왜 "배포"라 함? | 배포 = 내 컴이 아니라 **항상 켜진 클라우드 서버에 올려 운영**. 도커는 그 이전을 안전하게 해주는 수단. |
| 내 컴에서 하는 거 아님? | 개발/테스트는 내 컴. 운영(배포)은 내 컴 불가(꺼지고 외부접속 안 됨) → 클라우드로. |
| 남 컴에 깔기 편하려고? | 그것도 맞지만 **부수효과**. 본질은 환경 일관성 + 클라우드 이전 + 격리. |

## 5. 이 프로젝트와의 연결 (GPU 서빙 목표)
최종 목표 = 모델을 GPU로 서빙(Modal). 경로:
1. 모델 서버를 도커 이미지로 만든다 (작업4 완료)
2. 그 이미지를 클라우드 GPU(Modal)에 올린다 → **Modal은 도커 이미지를 받아 띄우는 방식**
3. 즉 **도커 이미지가 없으면 클라우드 GPU에 못 올린다.** 도커가 GPU 배포의 입장권.

→ devlog가 "Modal도 결국 이미지를 올린다"를 반복하는 이유. 지금 만든 Dockerfile이 GPU 트랙의 토대.

## 6. 한 줄 요약
도커는 "앱 + 환경 전체를 동결한 이미지"를 만들어 어디서든 똑같이 돌게 한다.
배포는 그 서비스를 내 노트북이 아니라 항상  하는 것이고,
도커는 그 이전을 "내 컴에선 되는데" 문제 없이 해주는 수단이다. 남 컴에 깔기 편한 건 부수효과.

## 보너스: Dockerfile / build / run 3단어 구분
- **Dockerfile** = 이미지를 어떻게 조립할지 적은 레시피 (실행 X)
- **docker build** = 레시피대로 이미지를 만든다 (이때 COPY로 코드가 이미지에 동결됨)
- **docker run** = 만든 이미지로 컨테이너를 띄운다 (이때 비로소 서비스 실행, CMD가 실행됨)
- 비유: 레시피 종이(Dockerfile) → 도시락 싸기(build) → 도시락 까먹기(run)
