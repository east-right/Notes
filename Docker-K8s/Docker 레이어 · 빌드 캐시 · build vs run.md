
## 0. 대전제 — build와 run은 완전히 다른 단계다

Dockerfile은 "서비스를 실행하는 스크립트"가 아니라 **"이미지를 조립하는 레시피"** 다.
헷갈리면 안 되는 두 단계:

| 단계 | 명령 | 하는 일 | 결과물 | 언제 |
|---|---|---|---|---|
| **빌드** | `docker build` | Dockerfile 명령을 한 줄씩 실행해 이미지를 조립 | 이미지(image) | 캐시는 **여기서** 발생 |
| **실행** | `docker run` / `docker compose up` | 완성된 이미지로 컨테이너를 띄움 | 컨테이너(container) | 빌드 끝난 뒤 |

- `COPY`, `RUN pip install` 같은 명령은 **빌드 때 딱 한 번** 실행되고 그 결과가 이미지 안에 동결된다.
- 맨 마지막 `CMD`(예: `uvicorn ...`)는 **빌드 때 실행 안 된다.** `docker run` 할 때 비로소 실행된다.
- **이미지 = 클래스(설계도), 컨테이너 = 인스턴스(실행체).** 이미지 1개로 컨테이너 N개를 띄울 수 있다.

> 즉 "캐시 재사용"은 전부 `docker build`(이미지 만드는 시점) 얘기지, 서비스가 돌아가는 시점(run)과는 무관하다.
---
## 1. 레이어(Layer)란 무엇인가

이미지는 통짜 파일 하나가 아니다. **읽기 전용 레이어들이 아래에서 위로 쌓인 스택**이다.
**Dockerfile의 명령어 한 줄 = 레이어 한 개**가 만들어진다.

```dockerfile
FROM python:3.12-slim                # 레이어 0: 베이스 OS + 파이썬
COPY requirements.txt ./             # 레이어 1: 파일 하나 추가됨
RUN pip install -r requirements.txt  # 레이어 2: 설치된 라이브러리들이 추가됨
COPY service/ ./service/             # 레이어 3: 앱 코드가 추가됨
```

각 레이어가 담는 것 = **"바로 이전 상태에서 바뀐 파일들의 변경분(diff)"** 뿐이다.
- 레이어 2는 "pip install로 새로 생긴 파일들"만 담는다.
- 레이어 3은 "복사해 들어온 service/ 파일들"만 담는다.

최종 이미지 = 이 레이어들을 아래에서부터 차곡차곡 겹쳐 합친 것(union). 위 레이어가 아래 레이어 위에 덮인다.

> 왜 이렇게 쪼개나? → ① 빌드를 빠르게(캐시), ② 배포를 가볍게(바뀐 레이어만 전송), ③ 여러 이미지가 공통 레이어를 공유. 아래에서 하나씩.

---
## 2. 빌드 캐시란 무엇인가

여기서 말하는 "캐시"는 브라우저 캐시 같은 게 아니라:

> **지난번 `docker build` 때 이미 만들어서 네 디스크에 저장해둔 레이어들.**

처음 빌드할 땐 캐시가 없어서 모든 명령을 실제로 실행한다. 그리고 각 명령의 **결과 레이어를 디스크에 저장**해둔다. 이 저장된 레이어들이 다음 빌드의 캐시가 된다.

---

## 3. "캐시 재사용"이 정확히 무슨 뜻인가

재빌드할 때 Docker는 Dockerfile을 위에서부터 한 줄씩 보며 매번 묻는다:

> **"이 명령어 + 그 입력이 지난번 빌드와 똑같은가?"**

- **똑같다** → 명령을 **다시 실행하지 않고**, 디스크에 저장돼 있던 그 레이어를 그대로 가져다 쓴다. (빌드 로그에 `CACHED` 표시) ← 이게 **캐시 재사용**
- **다르다** → 그 명령을 다시 실행해 새 레이어를 만든다.

### 타임라인 예시

**1차 build (캐시 없음 — 전부 실행):**
```
COPY requirements.txt   → 실행, 결과 레이어 디스크 저장 💾
RUN pip install ...      → 실행 (예: 3분 소요, 다운로드+설치), 레이어 저장 💾
COPY service/           → 실행, 레이어 저장 💾
```

**2차 build (service/ 코드만 한 줄 수정):**
```
COPY requirements.txt   → 입력(requirements 내용) 동일 → CACHED ✅ (실행 안 함)
RUN pip install ...      → 위도 그대로 + 명령 동일 → CACHED ✅ (3분 통째로 절약!)
COPY service/           → 코드 내용 바뀜 → 다시 실행 💾
```

비유: 라면 끓일 때 면을 매번 새로 반죽(캐시 없음) vs 똑같은 면이 이미 냉장고에 있으니 꺼내 씀(캐시 재사용). 입력(레시피)이 같으면 결과(면)도 같을 게 뻔하니 다시 만들 이유가 없다.

---

## 4. 캐시 무효화 규칙 (중요)

재사용이 언제 깨지는지를 알아야 Dockerfile을 잘 쓴다.

### 규칙 ① 무효화는 폭포처럼 "아래로만" 전파된다
한 레이어의 캐시가 깨지면 **그 아래(이후)의 모든 레이어도 무조건 다시 빌드**된다.
위 레이어가 바뀌면 그 위에 쌓이는 것들의 전제가 달라지므로 재사용이 불가능하기 때문.

```
COPY requirements.txt   ← 만약 여기가 바뀌면
RUN pip install ...      ← 여기도 깨지고 (CACHED 안 됨)
COPY service/           ← 여기도 깨진다 (전부 재실행)
```

### 규칙 ② 무엇이 "바뀜"을 판단하나 = 해시(지문)
각 레이어는 **`명령어 문자열 + 입력 파일의 내용`으로 만든 해시**로 식별된다.
- `COPY requirements.txt` → requirements.txt **내용**이 한 글자라도 바뀌면 해시가 달라짐 → 캐시 미스.
- `RUN pip install ...` → 명령 문자열이 같고 위 레이어도 그대로면 해시 동일 → 캐시 히트.
- 그래서 입력이 같으면 결과가 같을 게 보장되니 **안전하게** 재사용할 수 있는 것.

> 주의: `COPY`는 파일의 **내용**을 보지, 파일명만 보는 게 아니다. 코드 한 줄 수정도 그 COPY 레이어의 해시를 바꾼다.

## 5. 그래서 Dockerfile 작성의 황금 규칙

> **자주 안 바뀌는 것(의존성)을 위에, 자주 바뀌는 것(코드)을 아래에 COPY 하라.**

이유: 규칙 ①(아래로 전파) + 규칙 ②(내용 해시) 때문.
코드는 하루에 수십 번 바뀌고 의존성 목록은 거의 안 바뀐다. 무거운 `pip install`을 코드 **위**에 두면, 코드를 아무리 고쳐도 install 캐시가 살아남는다.

### 좋은 예 (실제 service/Dockerfile)
```dockerfile
COPY service/requirements.txt ./service/requirements.txt  # 의존성 먼저
RUN pip install --no-cache-dir -r service/re (캐시 대상)
COPY service/ ./service/                                    # 코드는 마지막
```
→ 코드 수정 시: 위 2줄 CACHED, 맨 아래만 재실행 → 빌드 몇 초.

### 안티패턴 (이렇게 하면 안 됨)
```dockerfile
COPY . .                                  # 전체를 먼저 복사하면
RUN pip install -r requirements.txt       # 코드 한 줄만 바뀌어도 위가 깨져 매번 재설치(수 분)
```

### 보너스: inference/Dockerfile도 같은 원리
`requirements 설치 → llama-cpp-python 소스 빌드(제일 무거움) → 앱코드 COPY` 순서.
코드를 고쳐도 그 끔찍하게 오래 걸리는 llama 소스 빌드를 다시 안 하기 위함.
(`--no-cache-dir`는 별개 개념 — pip이 다운로드 캐시를 이미지에 안 남겨 **이미지 용량**을 줄이는 옵션. Docker 레이어 캐시와는 다름.)

## 6. 배포에서 왜 중요한가 (덜 알려졌지만 진짜 가치)
레이어는 빌드 속도뿐 아니라 **이미지 전송(배포)** 에서도 핵심이다.

이미지를 레지스트리(Docker Hub, AWS ECR 등)에 `push`하거나 서버가 `pull`할 때:
- Docker는 레이어를 **콘텐츠 해시로 식별**하고, **이미 존재하는 레이어는 전송하지 않는다.**
- 즉 **바뀐 레이어만** 주고받는다.

### 시나리오
- app 이미지가 389MB. 코드 한 줄 고쳐서 재배포.
- 바뀐 건 맨 아래 `COPY service/` 레이어(수 MB)뿐.
- → 레지스트리엔 **그 수 MB만 push**, 나머지 베이스+의존성 레이어(약 380MB)는 "이미 있음"으로 스킵.
- → 배포 서버도 그 수 MB만 pull → **배포가 초 단위로 끝남.**

반대로 레이어 순서가 나빠 코드 변경이 의존성 레이어까지 깨면:
- → 매 배포마다 **380MB 전체를 다시 push/pull.**
- → CI/CD에서 하루에도 수십 번 배포하면 시간·네트워크(트래픽) 비용이 누적 폭발.

### 공유의 이점
여러 이미지가 같은 베이스(`python:3.12-slim`)를 쓰면 그 레이어는 **디스크/레지스트리에 한 벌만** 존재하고 공유된다.

### GPU/Modal 트랙과의 연결
서버리스 GPU(Modal scale-to-zero)는 트래픽이 없으면 컨테이너를 내렸다가 요청 오면 이미지를 다시 pull해 띄운다(콜드스타트). 이때 **레이어 캐시가 잘 돼 있으면 pull이 빨라 콜드스타트가 짧아진다.** 그래서 레이어 설계가 GPU 배포에서 더 중요해진다.

## 7. 한 페이지 요약

- **build ≠ run**: Dockerfile은 이미지를 조 스 실행(run)은 별개 단계다. 캐시는 build 시점 얘기.
- **레이어**: 명령 한 줄 = 레이어 하나, 변경분(diff)만 담음. 이미지는 레이어 스택.
- **캐시**: 지난 빌드가 디스크에 저장해둔 레
- **캐시 재사용**: 명령+입력의 해시가 같으면 재실행 없이 저장된 레이어를 그대로 씀.
- **무효화**: 한 레이어가 깨지면 그 아래 전  령+입력 내용 해시.
- **황금 규칙**: 안 바뀌는 의존성을 위, 자주 바뀌는 코드를 아래에 COPY → 빌드 빠름.
- **배포**: 레지스트리는 바뀐 레이어만 push/pull → 코드 변경 시 수 MB만 전송 → 배포 빠르고 대역폭 쌈. Modal 콜드스타트도 단축.
