## 메모리 관리와 GC
- 알다시피 파이썬은 객체지향 언어로써 가변 객체와 불변 객체가 존재한다.
- 즉 파이썬의 변수는 객체의 메모리 주소를 가지고 있어 그 주소의 객체를 보여주는 거지 실제 값을 가지고 있진 않는다.
	- 물론 불변 객체는 함수의 인자로 넘어갈 땐 실제 값을 던져 준다. -> 반대로 가변 변수는 메모리 주소를 던져준다. -> 그래서 이를 파이썬 에선 객체 참조에 의한 호출이라고 한다.
- 그래서 **모든 변수는 객체와 연결되어 있고 변수의 값을 바꾸면 삭제하고 거기 메모리에 새롭게 값을 쓰는게 아니다.**
	- 모두 재 할당의 경우 새로운 메모리를 할당 받고 거기에 값을 채워 넣고 연결한다.
	- 불변 변수의 경우 기존 변수에 수정이 일어나면 새로운 메모리를 할당 받고 거기랑 연결한다.
	- 가변 변수의 경우 기존 변수에 수정이 일어나도 메모리 값을 바꾸지 새롭게 할당 받지 않는다.(그래서 신경 써야되는 부분도 존재한다.)
- 즉 **파이썬의 변수를 변경하면 삭제가 일어나는게 아니라 새로운 메모리를 할당 받거나 해당 내용을 수정하는거다.**
- 이렇게 계속 새롭게 늘어나면 메모리가 버티질 못하니 메모리 정리 프로세스인 `Garbage Collector`가 존재한다.
- 그래서 파이썬의 Garbage Collector에는 두 가지 방식으로 객체를 찾고 삭제한다.
	- Reference Counting: 레퍼런스 카운팅, 즉 객체의 참조 횟수
	- Cycle detection: 순환 감지, 서로만을 참조하는 객체를 찾고 이를 삭제

- 참조 카운팅 혹은 레퍼런스 카운팅이다.
- 위 사진을 봤을 때 'hello'라는 객체는 a에 참조되고 있다. 그리고 a는 `sys.getrefcount()`라는 함수에 참조되어 사용되고 있다. 즉 사진에 대한 답은 2 이다.
	- 변수에 할당되거나 함수의 인자값으로 사용될 때 마다 참조 카운트가 1씩 늘어난다.
- 이제 여기서 `a='bye'`로 바뀌면 `'hello'`라는 객체는 참조 카운트가 0이 되어 버려 가비지 컬렉터에 의해 객체는 삭제된다.

## Cycle detection과 세대별 가비지 컬렉션
- 참조 카운팅에 만 의존하여 객체 메모리 관리를 하면 아래와 같은 문제가 발생한다.
```python
my_list = []
my_list.append(my_list) # 리스트 안에 자기 자신을 넣음

a = []
b = []
a.append(b)
b.append(a)
```
- 위와 같이 리스트와 같은 가변 객체가 자기 자신을 참조한다던가, 아니면 서로 참조한다던가 하면서 독립되어 있다면 실제로는 사용하지 않지만 계속 참조 카운팅이 0이 되지 않는 경우이다.
- 이러한 경우 메모리 해제를 못하기에 gc의 모듈은 주기적으로 각 객체의 참조 그래프를 분석하여 독립적인 순환참조에 대한 객체를 탐지하여 메모리를 회수한다.
- 엄청나게 많은 객체를 그래프로 분석한다는건 많은 비용을 초래하기에 자주 할 수 있는 작업은 아니다.
- 그래서 gc는 순환 참조 탐색을 세대별로 객체를 나누어 관리하는데 총 삼 세대로 정의하고 관리한다.
	- 0 세대 객체: 가장 최근에 생성된 객체, 일정 수 이상의 객체가 생성이 되면 해당 세대의 객체를 분석
	- 1 세대 객체: 0세대 객체에서 살아남으면 1세대 객체로 이동한다.
	- 2 세대 객체: 1세대 객체에서 살아남으면 2세대 객체로 이동한다. 제일 적게 검사한다.
![](assets/Pasted%20image%2020260425210035.png)
- 위 사진을 보면 가비지 컬렉터가 언제 실행되는 지(trigger) 즉 객체 생성 횟수를 알 수 있다.
- 사진에선 0세대의 객체가 700번 생성되면 gc가 실행되고, 1세대 2세대는 각각의 세대 객체가 10개 되는 순간 gc를 실행한다.

### 성능 저하와 최적화
- gc는 특정 상황에서 성능 저하를 초래한다.
	- 순환 참조가 많은 경우
		- 순환 참조가 많아 그래프 탐색의 횟수가 많은 경우
	- 객체 소멸과 생성이 매우 빈번한 경우
		- 매우 빈번하게 객체가 생성되면 0세대 가비지 컬렉션이 계속 실행된다.
	- 가비지 컬렉션 실행시 모든 작업 일시 중단
		- 가비지 컬렉션도 메모리에 영향을 주기에 스레드가 일시정지 된다.(스레드가 참조하는 메모리가 갑자기 삭제되면 안되니깐)
		- 멀티 스레드 프로그램에선 성능저하가 두드러진다.
- 실무에선 그래서 메모리 누수나 성능 저하가 보이면 gc의 가동횟수를 줄여야 하는데 trigger를 늘릴수 있지만 **최대한 순환참조를 최소화 하고 객체를 삭제하거나 객체를 최대한 재사용하는 것이 좋다**.
