## LLM 평가지표
- LLM은 기본적으로 Prefill과 decode 두 단계로 이루어져 문장을 생성한다.
- 여기서 말하는 LLM의 평가 지표는 속도에 관한 지표이지 특정 문제 혹은 도메인에 대한 평가지표는 아니라는 것을 말하고 싶다.
- 본문에서 말하는 평가지표는 LLM inference에 그 초점이 맞춰저 있으며 얼마나 빠르게 토큰을 생성하는지에 대해 주로 말한다.
- 이러한 LLM의 토큰 생성 속도 혹은 추론에 관한 지표는 대표적으로 `TTFT`, `ITl`, `E2EL` 등이 존재한다.

## 평가 지표 종류
#### TTFT(Time to First Token)
![](assets/Pasted%20image%2020260713161547.png)
![](assets/Pasted%20image%2020260713160703.png)
- 첫 요청을 보낸 후 첫 토큰을 생성하는 데 걸리는 시간을 말한다.
- 이는 모델이 얼마나 빠르게 응답을 시작할 수 있는지를 보여 준다.
- 토크나이징 모델의 성능과 속도 그리고 prompt로 들어온 내용의 Prefill의 계산 속도에 이 지표가 좌지 우지 된다.
	- 그래서 모델의 Prefill 단계를 평가하기 위한 지표로 많이 사용된다.
- 그 후 디코딩으로 첫 토큰을 생성 하는 것 까지의 시간을 지표로 활용한다.
#### E2EL(Total Latency)
![](assets/Pasted%20image%2020260713164552.png)
- 요청을 보낸 시점 부터 사용자가 최종 토큰을 수신하는 시점까지의 시간
- 총 Latency는 체감 응답성에 직접적인 영향을 미친다. 
- TTFT가 빠름에도 E2EL이 오래걸린다면 디코딩쪽 문제를 의심해 볼 수 있다.
- **Token Generation Time**
- $$Token Generation Time=E2EL – TTFT$$
	- 첫 토큰 생성 이후 모든 토큰이 생성되는 시간을 의미한다.
	- 즉 정석적인 디코딩의 성능 지표를 확인해볼 수 있다.
- **TPOT(Time per Out Token)**
	- 출력 토큰당 소요 시간으로 각 토큰을 연속적으로 생성하는데 걸리는 평균 시간 간격을 제시한다.
	- TTFT 제외 후 계산한다.
#### ITL(Inter-Token Latency)
![](assets/Pasted%20image%2020260713165222.png)
- ITL은 연속된 두 토큰 사이의 간격이고, 한(단일) 요청 안에서 ITL들을 평균 내면 TPOT와 같아진다. 그래서 두 용어가 혼용됨.
$$평균 ITL = TPOT = (E2EL − TTFT) / (총 출력 토큰 − 1)$$
- `−1`인 이유는 첫 토큰은 TTFT에 이미 포함돼 있어서 토큰 간 간격 수가 하나 적음
- 하지만 **여러요청(복합)일 때는 평균을 내는 방식이 달라 결과가 달라질 수 있다.**
**여러 요청 집계 시**

|지표|계산 방식|가중치|무엇을 보나|
|---|---|---|---|
|평균 TPOT|(TPOT₁ + … + TPOT_N) / N|**요청 가중**|요청 단위 체감 지연. 응답 길이 무관하게 모든 요청 동등 취급|
|평균 ITL|(모든 요청의 ITL 합) / (모든 요청의 총 토큰 수)|**토큰 가중**|시스템 전체 처리량·steady-state 스트리밍 속도. 긴 응답일수록 영향 큼|

→ 벤치마크 볼 때 **TPOT/ITL을 어떻게 정의했는지 반드시 확인**. 프레임워크·논문마다 달라서 같은 숫자도 해석이 바뀜.

## Mean / Median / P99
- 지연 시간은 **숫자 하나로 못 본다**. 같은 데이터를 어떤 통계로 요약하느냐에 따라 보이는 게 달라짐.

|지표|정의|무엇을 말해주나|약점|
|---|---|---|---|
|**Mean (평균)**|전체 합 / 개수|시간에 따른 **추세 모니터링**|이상치에 휘둘림. 느린 요청 하나가 평균을 부풀림|
|**Median (중앙값)**|정렬했을 때 가운데 값|**다수 유저의 체감**. 이상치에 강함|꼬리(tail)를 전혀 못 봄|
|**P99**|99%의 요청이 이 값 이하|**최악 1%의 경험** = tail latency. SLA 근거|노이즈에 민감할 수 있음|

> P90/P95도 자주 씀. P99가 너무 엄격하거나 노이즈에 흔들릴 때 대안.

**해석 감각**
- Median TTFT = 30초 → 대부분의 유저_가 30초를 기다린다는 뜻. 실시간 서비스면 사실상 사망.
- P99 TTFT = 100초 → 대다수는 괜찮지만 **소수가 심각하게 오래 기다린다**. 이 1%가 이탈·컴플레인의 진원지.

**세 개를 같이 봐야 하는 이유**
- Mean만 보면: 이상치에 속아 "괜찮은데?" 또는 "망했는데?" 둘 다 오판 가능
- Median만 보면: tail 문제를 완전히 놓침
- P99만 보면: 전체 분포가 어떤지 모름

그래서 벤치마크에서 `mean TTFT`, `median TPOT`, `P99 E2EL` 같이 **지표마다 다른 통계를 섞어서** 제시하는 걸 자주 보게 됨.

>**실무 포인트**: 프로덕션 튜닝은 대개 P99를 잡는 싸움이다. Mean/Median은 이미 괜찮은데 P99만 튀는 경우가 많고, 원인은 보통 큐 대기(배치 스케줄링), KV 캐시 압박에 의한 preemption, GC/콜드스타트 같은 것들 — 즉 모델 자체가 아니라 **서빙 스택**에 있다.
## RPS (Requests per Second)
- **정의**: 단위 시간에 **완료된** 요청 수. 시작한 요청이 아니라 끝난 요청이 기준이다. QPS(Queries per Second)라고도 부른다.

```
RPS = 완료 요청 수 / (T2 − T1)
```

- **본질적으로 무엇을 재는가**: 시스템의 _수용 능력(capacity)_. "동시에 몇 명을 감당할 수 있나"에 대한 답.

**Latency와의 연결 — Little's Law**
이게 RPS를 이해하는 핵심 다리다.
```
동시 처리 중인 요청 수 (concurrency) = RPS × 평균 E2EL
```

- 즉 **RPS와 지연시간은 독립 변수가 아니다.** 평균 E2EL이 2초인 시스템에서 RPS 50을 내려면 항상 100개 요청이 시스템 안에 떠 있어야 한다.
- 이 100개를 GPU가 감당 못 하면 → 큐가 쌓이고 → E2EL이 늘고 → 다시 concurrency가 늘고... 포화점 근처에서 지연이 폭발하는 이유가 이거다.

**LLM에서 RPS가 반쪽짜리인 이유**
- 전통 웹 서버는 요청 하나 = 대략 고정된 작업량(O(1))이라 RPS가 훌륭한 지표였다. LLM은 다르다
	- `"Hi"` → `"Hello!"` : 프리필 1토큰 + 디코드 2토큰
	- 2,000토큰 문서 → 800토큰 요약 : 작업량이 **수백 배**

- 같은 "1 request"인데 연산량이 100배 차이 난다. 그래서 **입출력 길이가 다른 워크로드끼리 RPS 비교는 무의미**하다.

**RPS가 여전히 유용한 경우**: 워크로드가 동질적일 때(고정 포맷 분류/추출 태스크), 그리고 **용량 산정과 SLO 계약**. "우리 서비스는 피크에 초당 30요청"은 비즈니스 언어고, 토큰은 아니다.

## TPS (Tokens per Second)
- **정의**: 초당 처리되는 토큰 수.
- **왜 토큰이 자연스러운 단위인가**: LLM의 연산량은 요청 개수가 아니라 **토큰 개수에 비례**한다. GPU가 실제로 하는 일의 단위가 토큰이다. RPS가 "손님 몇 명 받았나"라면 TPS는 "실제로 몇 접시를 만들었나"에 가깝다.

### Input TPS vs Output TPS — 하드웨어 병목이 다르다
- 이 둘을 나누는 진짜 이유는 단순히 "입력/출력"이 달라서가 아니라, **prefill과 decode가 완전히 다른 자원에서 병목이 걸리기 때문**이다.

|-|Input TPS (Prefill)|Output TPS (Decode)|
|---|---|---|
|하는 일|프롬프트 전체를 한 번에 forward|토큰 1개씩 순차 forward|
|병렬성|모든 토큰 동시 처리 → GPU 꽉 채움|토큰당 1개씩 → GPU 놀음|
|**병목**|**Compute-bound** (FLOPs)|**Memory bandwidth-bound** (가중치 로딩)|
|배칭 효과|이미 포화라 효과 제한적|**효과 절대적** (같은 가중치 읽어서 N개 처리)|
|민감한 워크로드|긴 문서 요약, RAG(긴 컨텍스트)|챗봇, 코드 생성 (짧은 입력 → 긴 출력)|

디코드가 memory-bound라는 게 왜 중요하냐면 — **배치를 키워도 GPU 연산은 거의 안 늘고 처리량만 늘어난다.** 어차피 모델 가중치를 HBM에서 한 번 읽어오는 비용이 지배적인데, 그 한 번 읽어온 걸로 1개를 처리하든 64개를 처리하든 비슷하다. continuous batching, PagedAttention 같은 게 존재하는 이유가 전부 여기에 있다.

### TPS의 또 다른 함정 — "누구의 TPS인가"

이건 input/output 구분보다 더 자주 사고를 낸다.

|-|의미|계산|
|---|---|---|
|**시스템 총 Output TPS**|모든 동시 요청 합산 처리량. 서빙 효율·비용 지표|Σ(모든 요청의 출력 토큰) / 시간|
|**사용자당 Output TPS**|개별 사용자가 체감하는 스트리밍 속도|**1 / TPOT**|

**예시**: "우리 시스템 output TPS = 2,000 tok/s!" → 근데 동시 사용자 100명이면, **사용자 1명당 20 tok/s**. TPOT 50ms. 사람 읽기 속도(대략 10~15 tok/s)보다 아주 약간 빠른 수준이다.

같은 2,000 tok/s인데 동시 사용자 10명이면 사용자당 200 tok/s — 완전히 다른 서비스다. **총 TPS 숫자만으로는 체감 품질을 전혀 알 수 없다.**

### 관계식

```
TPS ≈ RPS × 요청당 평균 토큰 수
사용자당 Output TPS = 1 / TPOT
시스템 Output TPS ≈ 동시 요청 수 / TPOT
```

마지막 식이 트레이드오프의 전부다. **동시성을 올리면 시스템 TPS는 오르지만 TPOT도 같이 나빠진다.** 공짜가 아니다.

## 그래서 셋을 같이 봐야 한다

```
RPS   → 비즈니스 용량 (몇 명을 받나)
TPS   → GPU 효율 / 비용 (토큰당 얼마인가)
Latency (TTFT/TPOT/P99) → 사용자 체감 (쓸만한가)
```

**어느 하나만 최적화하면 나머지가 무너진다.** 배치를 극단적으로 키우면 TPS와 RPS는 최고 기록을 찍지만, TTFT는 큐 대기로 터지고 TPOT는 늘어져서 아무도 안 쓰는 서비스가 된다. 반대로 배치=1로 지연만 잡으면 GPU 비용이 감당이 안 된다.

실무에서 하는 일은 결국 이거다: **"P99 TTFT < X, TPOT < Y를 만족하는 선에서 TPS를 최대로"** — 지연 SLO를 제약 조건으로 걸고 처리량을 최대화하는 것.


## Latency vs. Throughput 트레이드오프
앞서 나온 "동시성 올리면 TPS↑ TPOT↓"의 정식 버전. **두 목표는 근본적으로 같은 GPU를 놓고 싸운다.**

### 세 가지 지향점

|목표|전략|대가|
|---|---|---|
|**처리량 최대화** (TPS/MW)|큰 배치, 공유 컴퓨트. 와트당 토큰 수를 짜냄|개별 사용자 응답이 느려짐|
|**지연 최소화** (사용자당 TPS)|작은 배치, 격리된 컴퓨트. 낮은 TTFT|GPU를 놀림 = 비효율 = 비용|
|**동적 균형**|워크로드·사용자 우선순위·SLO에 따라 실시간 튜닝|복잡도. 대신 SLO가 다른 여러 앱을 한 스택에서 서빙 가능|

> `TPS/MW`(와트당 토큰)라는 단위에 주목. **결국 처리량 최적화는 비용/전력 최적화**다. 지연 최적화는 사용자 경험 최적화고. 둘은 애초에 다른 화폐로 계산된다.

### 워크로드별로 봐야 할 지표가 다르다

|유스케이스|핵심 지표|이유|
|---|---|---|
|대화형 챗|**TTFT** → 그다음 ITL/TPOT|언제 시작되나 + 매끄럽게 흐르나|
|롱폼 스트리밍|**ITL/TPOT + E2EL**|첫 토큰 이후엔 생성 속도가 지배|
|에이전틱/멀티스텝|**E2EL**|다음 스텝이 응답 **전체**를 기다림. 스트리밍이 무의미|
|대량 오프라인 배치|**TPS + 토큰당 비용**|개별 요청 지연은 아무래도 상관없음|
|지연 제약 온라인 서비스|**Goodput**|SLO를 만족한 요청만 "성공"으로 셈|

**핵심 포인트 하나**: 에이전틱 워크플로에서 TTFT 최적화에 힘 쏟는 건 헛수고다. LLM이 첫 토큰을 얼마나 빨리 뱉든, 다음 툴 호출은 응답이 **끝나야** 시작한다. 여기선 E2EL만 본다. 반대로 챗봇에서 E2EL만 보면 사용자가 왜 떠나는지 영원히 모른다.

### Goodput — 새로 나온 개념
일반 throughput은 **"완료된 요청 수"**만 센다. Goodput은 **"SLO를 만족하면서 완료된 요청 수"**만 센다.

```
Throughput = 완료 요청/초
Goodput    = (TTFT < X ms AND TPOT < Y ms) 를 만족한 완료 요청/초
```

왜 중요하냐 — 배치를 키워서 TPS 숫자를 부풀렸는데 그중 절반이 TTFT SLO를 못 지켰다면, **그 절반은 사용자 입장에서 실패한 요청**이다. 처리는 했지만 값어치가 없다. Goodput은 이 자기기만을 차단한다. **"진짜 쓸모 있는 처리량"** 지표.

### 튜닝 노브(knobs)
시스템 레벨에서 돌릴 수 있는 다이얼들:
- **DP / TP / EP** — Data / Tensor / Expert Parallelism
- **배치 크기**
- **정밀도** — FP8, FP4 등 양자화
- **Disaggregation** — prefill과 decode를 **분리된 하드웨어**에 배치

마지막 게 특히 흥미로운데, 앞서 정리한 "prefill=compute-bound, decode=memory-bound"에서 자연스럽게 따라오는 결론이다. 성격이 다른 두 단계를 한 GPU에 섞어두면 서로 방해한다(긴 prefill 하나가 진행 중이던 decode들을 멈춰 세워서 ITL을 튀게 만드는 식). 아예 물리적으로 분리하면 각각을 독립적으로 최적화할 수 있다.

**중요한 건 이거다**: 모든 노브는 **한 곳을 개선하면 다른 곳에 비용을 전가한다.** 공짜 다이얼은 없다.

### 결론
> **최고의 구성 = 최고 처리량도, 최저 지연도 아니다. 내 워크로드의 SLO를 만족하는 구성이다.**

그리고 실무적 함의 하나 — **서버리스 API는 이 노브들을 전부 추상화해서 감춘다.** 편하지만 튜닝 여지가 없다. 반대로 vLLM/SGLang 같은 걸로 직접 스택을 짜면 트레이드오프를 내 손으로 항해할 수 있다. 어느 쪽이 맞는지는 SLO가 얼마나 빡센가에 달렸다.
