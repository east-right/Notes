- 테이블 내의 데이터의 고유성을 나타내기 위해 PK에 유니크한 값을 두는 경우가 존재한다.
- 이 아이디는 주로 PK로 들어가기 때문에 인덱스가 자동으로 생성된다. 그래서 이 ID의 전략을 짜는 부분으은 매우 중요하다.
- 해당 아이디는 직접 생성하는 방식은 단일 시스템일 때와 분산시스템 일때 차이가 상이하다.
- 단일 시스템은 직접 생성하던가 간단한 rule 기반으로 만들면 된다.
- 직접생성하는 방식이라고 적었지만 오라클 기준 **시퀀스**를 사용하여 생성하는 방식이 가장 기본이다.
	- 이는 DF의 index를 생각하면 쉽다. 그냥 들어오는 순새대로 오름차순 정렬을 한다.
	- mysql에는 `auto_increment`라는 id 생성기가 있다. 오라클의 시퀀스랑 다르게 생성기를 따로 두지 않고 insert시 제약조건에 붙여서 사용하면 max값을 보고 붙힌다.
	- 해당 방식을 응용하여 ID를 생성할 때 특수한 패턴을 만들 수 있다.
		- 제품 테이블을 만들 때 카테고리별 id 할당 테이블을 추가하여 카테고리+시퀀스 조합으로 생성
- 이제 이 분산 환경에서의 ID 생성은 또 이야기가 많이 달라진다.
	- 분산 시스템에서는 순차적으로 번호를 따는 행위 자체가 병목이 되기 때문에 `의미를 담은 순차 ID` 방식의 ID는 피하는 추세
	- 그래서 분산 시스템에서는 `UUID`나 `Snowflake ID`와 같은 시간 기반의 유니크 난수를 사용하여 충돌없이 무한대로 생성하는 방법을 주로 사용한다. 추가로`NanoID`가 존재한다.

## UUID
![](assets/Pasted%20image%2020260403170800.png)
- UUID는 유일성이 보장되는 128 비트의 16진수로 이루어진 숫자
- 128비트의 16진수로 이루어져있어 중복될 가능성이 매우 낮다.
- UUID의 구성으로는
	- time 시리즈
	- clock_seq_hi_and_res
		- 레이아웃과 클럭 시퀀스 조합
	- node
		- mac 주소, 네임스페이스, 이름 등을 기반으로 node id 생성
**장점**
- 분신 시스템, 멀티 인스턴스 등 다양한 환경에서 유일한 ID로 활용 가능
- 쉬움
**단점**
- 128ibt 이므로 크기가 너무큼, 인덱스로 활용 시 공간 효율성이 매우 나쁨
- 읽고 이해하기 힘듬
- 정렬 불가능 랜덤인수이기 때문에

## Snowflake ID
![](assets/Pasted%20image%2020260403171227.png)
- 많은 트래픽을 처리하는 분산 환경 트위터에서 사용하는 방식
- **Snowflake ID는 유일성을 보장하는 64bit의 10진수로 이루어진 숫자**
- 각 데이터의 고유한 ID를 생성하기 위해 Snowflake ID기법 고안
- Snowflake ID는 총 4개의 부분으로 구성됨
	- **sign** (1bit) :  
	    - 음수와 양수를 구별하는 데 사용하며, 큰 용도는 없음
	- **timestamp** (41bit) : 
	    - 기원 시각(epoch) 이후로 몇 밀리초가 경과했는지 나타내는 값
	- **worker_id** (10bit) :
	    - 데이터 센터 ID 5bit + 서버 ID 5bit : 데이터 센터 max 32개 * 데이터 센터 당 서버 max 32대 = 1,024대까지 가능
	    - 고유한 인스턴스 ID 10bit : 인스턴스 1,024대까지 가능
	- **sequence** (12bit) :
	    - ID를 생성할 때마다 1만큼 증가시키는 값이며, 1밀리 초가 경과할 때마다 0으로 초기화된다.

**장점**
- 64bit 크기로, GUID 표준에 비해 작은 크기를 가지고 있다.
- timestamp 기반으로 생성되기 때문에 정렬 가능하다.
- 중앙 집중 ID 채번 방식이 사용가능 하다.
**단점**
- timestamp 기반으로 생성되기 때문에 OS별, 인스턴스별 시간 차에 유의해야 한다.
- UUID에 비해 사용 방법이 복잡하다.
- 중앙 집중 ID 채번 방식(Zookeeper 혹은 Thrift 활용)을 사용한다면 네트워크 통신이 필요하며, 관리해야 하는 포인트가 늘어난다
