#오라클 #db #dba #cdc #마이그레이션
- 데이터 마이그레이션은 데이터를 한 시스템이나 스토리지 환경에서 다른 환경으로 이동시키는 프로세스를 의미한다.
- 단순히 파일을 복사해서 옮기는 형식이 아닌 데이터 형식의 변환, 동시에 무결성 검증, 비즈니스 로직에 따른 혹은 비즈니스 가용성 확보를 위해 데이터 저장 형식을 변경하는 공학적 절차를 포함한다.
- 스토리지, 데이터베이스, 애플리케이션, 클라우드 마이그레이션 등 다양한 종류의 마이그레이션으로 분류 되고 각 방법 마다 상이한 기술이 요구된다.

## 데이터 절차와 마이그레이션 ETL
- 마이그레이션의 기본 굴곡은 추출(Extraction), 변환(Transformation), 로드(Loading)의 세 단계로 구성되는 ETL 프로세스에 기반한다.
	- 추출: 현재 저장되어 있는 소스 시스템의 구조를 분석 후 이관 대상을 식별한다. 그 후 데이터 소스의 식별과 더불어 추출 쿼리/작업을 진행하여 데이터를 뽑는디ㅏ.
	- 변환: 추출된 데이터를 마이그레이션 이관 대상 시스템의 형식, 유형, 길이에 적합하도록 가공하는 단계, PK, FK를 철저히 검사하며 중복제거 밑 이상 데이터 정제 작업이 핵심으로 이루어 진다.
		(요즘은 마이그레이션 할 때 FK는 설정 안한다.)
	- 로드: 변환이 완료된 데이터를 최종 타깃 환경에 배치하는 단계이다. 로드 작업 이후에는 이관된 데이터가 실제 비즈니스 로직에 따라 정상적으로 사용될 수 있는지 확인하는 실행 및 검증 절차가 필수적
-  마이그레이션 life-cycle은 철저히 관리 되어야 한다.
	- 사전 마이그레이션: 데이터 소스 식별, 품짐 평가, 요구사항 정의, 보안 표준 검토
	- 마이그레이션: 데이터 변환 로직 코딩, 실시간 모니터링, 세그먼트별 반복 이관
	- 사후 마이그레이션: 성능 평가, 데이터 조정 테스트, 호환성 검증(서비스)
- ETL은 주로 배치 방식으로 작동한다. 이는 정해진 주기마다 대량의 데이터를 한 번에 처리하는 방식
	- 하루에 한 번 자정마다 전날의 모든 거래 데이터등을 모아 분석 시스템으로 옮기는 작업
- ETL의 배치 처리 방식은 아래와 같은 한계를 가진다.
	- 실시간성 부족
	- 운영 DB(source DB)에 성능 영향
		- 대량의 데이터를 추출하는 과정에서 상당한 부하를 줌
	- 비효율적인 자원 사용

## ETL과 다른 데이터 전달 방식 ELT
- 빅데이터 시대에 접어들면서 하둡과 같은 분산 저장 시스템의 등장으로 데이터를 쌓아둘 수 있는 경우 먼저 정제되지 않는 원천 데이터를 쌓아 두는 경우가 생겼다.
- ELT한 데이터를 일단 먼저 추출 적재를 우선하고 이후 변환을하는 프로세스를 의미 한다.
- 이러한 관점에서 ETL은 비즈니스 로직이 앞에 있다면 ELT는 비즈니스 로직이 뒤에 있다.

## 제로 다운타임 마이그레이션
- 현대 비즈니스 환경에서 가동 중단은 매출 손상뿐 아닌 브랜드 평판 저하까지 이루어 지는 아주 치명적인 결과를 초래한다.
- 그래서 `제로 다운 타임 마이그레이션`은 단순한 선택이 아닌 필수로 작용한다.
- 해당 방식을 사용하기 위해서는 실시간으로 변하는 데이터(서비스 중인)에도 가용성을 유지하도록 설계되어야 한다.
- 이전 버전의 애플리케이션이 신규 저장소의 데이터 구조에 호환이 되어야 하며 반대로 신규 에플리케이션도 구 데이터 구조와 통신이 가능하여야 한다.
- 다양한 방법이 있겠지만 업계에서 가장 표준이 되는 방법은 `CDC(Change Data Capture)`이다.

## CDC
![](assets/Pasted%20image%2020260401215314.png)
- 제로 다운타임 마이그레이션(이하 ZDM)을 하기 위해 가장 많이 사용되는 방식은 CDC 방식이다.
- CDC의 정의는 **데이터 베이스 내 데이터의 insert, update, delete 등과 같은 변경사항을 감지하고 이걸 캡쳐해서 다른 시스템으로 실시간으로 옮기는 작업을 말한다.**
- 즉 CDC의 기본 기조는 데이터를 복사하는게 아닌 변화를 실시간으로 추적하여 이 변화를 다른 시스템에 전달하여 사용하는 방법이다.
-  근데 알아야하는 부분이 CDC는 무 중단 마이그레이션을 할 때 많이 사용한다 이지 MSA(마이크로서비스 아키텍처) 환경에서 서비스간 실시간 이벤트를 주고 받거다, 검색 엔진에 데이터를 실시간 동기화할 때 쓰는 범용적인 스트리밍 기술이다.
- CDC의 종류는 아래와 같다.
	- **로그기반 CDC**
		- 데이터 베이스의 **트랜잭션 로그**를 분석하여 데이터 변경 사항을 감지한다. 부하가 거의 없고 데이터 변경을 순서대로 정확하게 포착할 수 있다.
	- 트리거 기반 CDC
		- 데이터 베이스의 테이블에 트리거를 설정하여 데이터 변경이 발생할 때마다 해당 내용을 별도의 테이블에 기록, 이를 통해 변경 사항을 추적.
		- 구현이 간단하지만 운영 DB에 직접적인 부하를 안겨줌
	- 쿼리 기반 CDC
		- 테이블의 특정 컬럼(최종 수정일시)를 주기적으로 쿼리하여 변경된 데이터를 식별하는 방식
		- 구현은 간단하지만 삭제 데이터 감지는 매우 어렵고 실시간성이 떨어지는 단점이 존재
- CDC의 활용 시나리오는 아래와 같다.
	- 대규모 스케일 아웃
		- 여러 데이터베이스에 데이터를 분산 저장하고 CDC를 통해 변경 사항을 동기화
	- 이기종 DBMS 간 복제
		- Oracle에서 Postgregql로 또는 RDBMS에서 NoSQL 데이터베이스로 실시간 복제
	- DR(재해 복구) 시스템 구축
		- 운영 데이터베이스의 변경 사항을 실시간으로 재해 복구 센터의 데이터베이스에 복제하여 장애 발생 시 데이터 손실을 최소화하고 빠른 복구 시스템 구축에 사용
	- 무중단 마이그레이션(ZDM)
		- 서비스를 중단하지 않고 기존 데이터베이스를 새로운 데이터베이스로 이전할 때, CDC 기술을 사용하여 마이그레이션 중 발생하는 데이터 변경 사항을 신규 데이터 베이스에 실시간으로 반영
	- 부하 분신 시스템 구축
		- 읽기 전용 복제본을 여러 개 만들고 CDC를 통해 원본 데이터베이스와 동기화 하여 읽기 작업의 부하를 분산
		- 이게 데이터 웨어하우스
- 주요 cdc 기반 복제 솔루션은 아래와 같다.
	- 상용 CDC 서비스
		- Qlik Replicate
		- x-log for CDC
		- OGG(Oracle Golden Gate) - datapump를 진행함
	- 오픈소스 서비스
		- Debezium(Kafka) - 이게 제일 언급이 많음
		- apache flink - 이거도 결국 Debezium 사용 변환 단계에서 이걸 사용할때 인듯
	- 클라우드
		- AWS DMS
			- 클라우드 CDC의 대명사 AWS 환경(RDS, Aurora, S3, RedShift)에 관한 데이터 연결이라면 무조건
			- 초기 스냅샷 + CDC 복제 같이 되는 솔루션 스키마 번역도 있어서 이기종으로 넘어갈 때 좋음
		- GCP DataStream
			- google판 CDC로 구글 최강의 무기인 BigQuery(데이터 웨어하우스)로 꽃아 넣을때 큰 장점
		- Azure DMS

## CDC 작동 순서와 방법
- 대규모 기존 데이터베이스의 경우 네트워크 성능 및 기타 제약으로 인해 트랜잭션 로그에서 전체 기록을 읽고 던지는건 비실용적이다.
- 일반적으로 먼저 일괄 load(일괄로 데이터 집어 넣음)을 수행한 다음 CDC를 사용하여 동기화 한다.
- 프로세스 순서
	1. 특정 시점에 데이터베이스의 일관된 스냅샷 또는 백업을 만든다.
		- 첫 적재는 오래걸릴 수 있다.
	2. 대규모 스냅샷을 대상 시스템에 로드
	3. 스냅샷이 촬영된 정확한 로그 위치에서 CDC 스트림을 시작
